# Verifiable Intent profile (draft v0.1) — implementation notes

Package: `packages/vi-profile/aaw_vi`. Version string: `verifiable-intent-draft-v0.1@356c296`.

The reference implementation (`src/verifiable_intent` at commit `356c296`) is vendored **unmodified**
under `packages/vi-profile/vendor/` with its Apache-2.0 licence. It performs all VI issuance
(`create_layer1`, `create_layer2_autonomous`, `create_layer2_immediate`, `create_sd_jwt`) and chain
verification (`verify_chain`, `check_constraints`, `verify_checkout_hash_binding`). The adapter only
maps the wallet's grant model onto VI layers, selects role-specific disclosures, pins the clock, and
converts results into the application's diagnostic. Its own tests (326) pass on Python 3.9 and 3.12.

## Layers as used here

| Layer | Producer | typ | Content |
| --- | --- | --- | --- |
| L1 | test issuer | `sd+jwt` | `vct urn:aaw:test:vi-user-credential:1`, `cnf` = user device key, `email` selectively disclosable (never presented) |
| L2 | user signing component | `kb-sd-jwt+kb` (autonomous) / `kb-sd-jwt` (immediate) | open (or final) checkout + payment mandates, merchants and acceptable items as standalone disclosures; `sd_hash` over the bare L1 |
| L3a | agent | `kb-sd-jwt` | `mandate.payment.1` for the payment verifier; `sd_hash` over the L2 presentation as sent to that verifier |
| L3b | agent | `kb-sd-jwt` | `mandate.checkout.1` (with `checkout_jwt`) for the merchant |

Constraint types: `mandate.checkout.allowed_merchants`, `mandate.checkout.line_items`,
`mandate.payment.amount_range`, `mandate.payment.allowed_payees`, `mandate.payment.reference`
(injected by the reference L2 builder). These are distinct from AP2's constraint identifiers; the two
profiles share no parser.

## Behaviour that differs from AP2 (and is preserved)

* **Immediate mode discloses both final mandates to each verifier.** The reference verifier requires
  both `mandate.checkout.1` and `mandate.payment.1` in an immediate-mode L2, so role-scoping applies
  only to autonomous mode (split L3). The payment view therefore includes the checkout mandate in
  immediate mode; the evidence viewer flags this as a warning.
* **A `line_items` constraint is mandatory** in every open checkout mandate. Grants without SKU
  restrictions use the reference implementation's wildcard form (`acceptable_items: []`) with a
  100-unit total-quantity cap.
* **One L3a+L3b pair per mandate pair** (spec README §11, security-model §4.2). After a definitive
  non-execution the grant becomes `requires_new_authorization`; the agent must obtain a new L2.
* `aud` on the L2 is the agent identifier in autonomous mode and the merchant website in immediate
  mode (one signature, two verifiers); the payment verifier does not enforce L2 `aud` in immediate mode.

## Hardening the adapter adds on top of the reference verifier

* Every disclosure presented in L1/L2/L3 must be referenced by a digest; stray disclosures are
  rejected (`UNEXPECTED_DISCLOSURE` / `DISCLOSURE_DIGEST_MISMATCH`).
* Undisclosed `{"...": digest}` references inside constraints are **kept** when resolving, so an
  agent cannot turn a non-empty `acceptable_items` list into a wildcard by withholding disclosures.
* The reference checker treats "all allowed entries undisclosed" as a skip; the adapter fails closed
  (`MISSING_REQUIRED_DISCLOSURE`).
* Constraints are evaluated one at a time in `STRICT` mode with open-mandate semantics so each gets its
  own satisfied/violation record and unknown types fail.
* Issuer keys come from the trust store (`iss`, `kid`), never from the credential.
* The reference verifier reads `time.time()`; the adapter pins it to the injected clock during
  verification so expiry boundaries are deterministic.

## Fixture provenance

`fixtures/vi/reference_autonomous.json` is generated by `fixtures/vi/generate_reference_fixture.py`
using only the vendored reference implementation and its example key scalars from
`examples/helpers.py` (fixed time `1790400000`). `tests/crypto/test_vi_profile.py` verifies it with
our adapter and, in the other direction, verifies our adapter's artifacts with the reference
`verify_chain` directly.
