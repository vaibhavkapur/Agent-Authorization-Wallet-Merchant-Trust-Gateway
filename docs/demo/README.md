# Demo guide

## Setup

### Option 1 — single process (no Docker, SQLite)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH=packages/signer-interface:packages/authorization-domain:packages/ap2-profile:packages/vi-profile:packages/vi-profile/vendor:packages/tap-verifier:packages/execution-coordinator:apps/api:apps/merchant-gateway:apps/test-issuer:apps/test-registry
AAW_FIXED_CLOCK=1 uvicorn aaw_api.main:app --reload --port 8000     # gateway/issuer/registry embedded
cd apps/web && npm install && NEXT_PUBLIC_API_URL=http://localhost:8000 npm run dev
```

`AAW_FIXED_CLOCK=1` makes `POST /v1/demo/clock/advance` available for expiry / stale-claim demos.

### Option 2 — docker-compose (PostgreSQL, separate services)

```bash
docker compose up --build
# web http://localhost:3000 · api http://localhost:8000/docs · gateway :8010 · issuer :8020 · registry :8030
```

Demo tokens are exposed by `GET /v1/participants` because `AAW_EXPOSE_DEMO_TOKENS=1`.

### Tests

```bash
source .venv/bin/activate && python -m pytest -q      # 69 tests: crypto, protocol, concurrency, recovery
```

## Scenarios (web → “Demo & failure injection”, or `POST /v1/agent/purchase`)

| Demo | What happens | Expected outcome |
| --- | --- | --- |
| A — valid autonomous purchase | grant: 1 purchase ≤ $150 at merchant A or B; agent buys $120 headphones | `ALLOW`, claim `consumed`, grant `consumed`, checkout + payment receipts |
| B — authentic request, invalid purchase | agent buys the $155 speaker | TAP `valid`; `REQUIRE_NEW_AUTHORIZATION` with `DELIVERED_TOTAL_EXCEEDS_LIMIT` (`15500` vs `15000`); grant still active |
| C — checkout tampering | payee altered after signing / agent signs $1 payment / undelegated agent key; direct-mode: approved checkout A presented for checkout B | `DENY`: `DISCLOSURE_DIGEST_MISMATCH`, `PAYMENT_BINDING_MISMATCH`, `AGENT_KEY_MISMATCH`, `CHECKOUT_BINDING_MISMATCH` |
| D — replay and concurrency | same signed request twice; freshly signed retry; second purchase on the same grant; 6 concurrent purchases (test) | `REQUEST_REPLAY` (401); idempotent replay of the original result; `AUTHORIZATION_CONSUMED`; exactly one execution |
| E — private evidence views | open an execution, switch merchant / payment / user / auditor tabs | merchant view has no payment mandate, no other merchant, no identity; payment view has no line items |
| Recovery | `fault=lose_response`, `crash_before_submit`, `decline` | `RECONCILIATION_REQUIRED` → worker settles from the processor ledger; stale claim → `resolved_not_executed`; AP2 grant returns to `active`, VI grant becomes `requires_new_authorization` |

### Direct (human-present) flow

Select *Direct* on the Delegate page: the merchant issues the final checkout first, the review screen
shows exact items, total and checkout hash, the user signs closed mandates, and the agent can only
complete that checkout.

## Reading the diagnostic

```json
{
  "decision": "REQUIRE_NEW_AUTHORIZATION",
  "request_authentication": "valid",
  "delegation_verification": "valid",
  "constraint_verification": "failed",
  "binding_verification": "valid",
  "execution_state": "valid",
  "reason_codes": ["DELIVERED_TOTAL_EXCEEDS_LIMIT"],
  "evaluated_total_minor": "15500",
  "authorized_max_minor": "15000",
  "currency": "USD"
}
```

Decisions: `ALLOW`, `REQUIRE_NEW_AUTHORIZATION` (the grant would permit a different purchase),
`DENY` (invalid evidence or disallowed action), `RECONCILIATION_REQUIRED` (uncertain prior execution).

## Observability

`GET /v1/metrics` reports verification latency per verifier role, rejection reasons, replay attempts,
authorizations expiring or expired, and unresolved executions. Screenshots should use the synthetic
identities and redacted evidence views only.
